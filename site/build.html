Building

The PC reference build is upstream's. The Xbox build uses the nxdk toolchain and the scripts in tools/.

PC reference build

The build system is unchanged from Xash3D FWGS:

./waf configure -T release
./waf build

ref/gl stays alive until the Vulkan renderer matches it; it is the only thing that tells us what correct looks like.

Xbox build

The toolchain is in deps/nxdk. nxdk has no dynamic library loading, so everything is linked statically into the XBE.

ScriptWhat it does
tools/xbox-sweep.sh engineCompiles every engine C file for the Xbox and summarises the failures.
tools/xbox-game-link-check.sh hl --include-client --include-freevgui --xbe <path> Links the Half-Life default.xbe.
tools/xbox-xiso.shPacks a disc from it.

Conventions, gates and the rules for contributions are in AGENTS.md in the repository.

The asset baker

tools/asset-studio is a separate CMake project that builds for the host, not the console. It reads a retail install and writes the .mpak archives, the DXT1 skies and the music files. The packager runs it for you; the Windows exe carries a copy. On Linux, build it first with cmake and g++:

python3 tools/packager/build_baker.py

The packager

python tools/packager/build_baker.py                              # builds bin/AssetStudio
python tools/packager/make_payload.py --xbe <clean main build>   # builds payload/
python tools/packager/release.py --xbe <build> --version vX.Y   # builds, does not publish
python -m unittest discover -s tools/packager/tests              # tests

release.py needs PyInstaller. The Windows exe is built on Windows; Linux users get the portable zip. A release carries the stable Xbox build: a clean build of main, and the release notes name its commit.

Testing in an emulator

The scripts tools/xemu-*.sh run builds in xemu, the Xbox emulator used for development. An emulator does not replace the console for performance numbers.
