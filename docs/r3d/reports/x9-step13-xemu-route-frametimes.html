Frame-time recorder: scripted route in xemu

A scripted run with the version-2 recorder: host_frametime_analysis 1, then map c1a0 and changelevel to c1a0e, c1a0d and c1a0a, about 20 s each, no input (the view stays at each map's spawn). 2,247 frames, four map changes, and per frame the renderer's work counters. The times are xemu's; the counters are what the console would submit for the same views. Each changelevel frame counts its work twice: the loading screen is drawn from outside Host_Frame within that frame's span, so the peak column equals two frames of work there.

Recorded in xemu. The times are the emulator's on a PC, not a Pentium III and an NV2A: xemu caps presentation at the 60 Hz refresh, its TSC is not the console's clock, and its GPU wait says nothing about the real GPU. The work counters (draws, vertices, pushbuffer, texture binds, lightmap texels...) are counts, not times: they are the same as on the console, so they can drive an optimisation decision from an xemu run; the times and their correlation with the counters need the console.

Work per frame

What the renderer submitted in each in-play frame, counted where ref/nv2a submits it: mean / peak per map. These are counts, not times, so they are the same in xemu as on the console — an xemu run measures them exactly. Draws are draw submissions (a world run, a 2D/TriAPI batch, a decal); prims the BEGIN/END blocks they split into; PB KiB the pushbuffer written in the frame; verts every vertex or index submitted (world, studio, TriAPI, 2D, decals); LM texels the lightmap texels rebuilt on the CPU.

What the frame time follows

Over every in-play frame of the session: each counter's mean and peak, and Pearson's r against the frame's CPU time and its GPU wait. A strong r says the time rises and falls with that work. In xemu the times are the emulator's, so these r values describe xemu, not the console.

CPU and GPU

Each frame is timed with the Pentium III's time-stamp counter, calibrated against the kernel's performance counter (733.33 MHz in this file). CPU is the engine's own work: Host_Frame minus the renderer's waits. GPU wait is the time the CPU spun on pb_busy() because the GPU still had work queued. The NV2A runs in parallel with the CPU and pbkit exposes no GPU-side timestamp, so this is the GPU's excess over the CPU, not its busy time: near zero means the GPU kept up and the frame was CPU-bound; a large value means the GPU held the frame. GPU-bound counts frames with more than 1 ms of GPU wait.

Waits and the rest

vblank / swap is time in pb_wait_for_vbl() and in pb_finished() while all three back buffers were queued for display. Between frames is the time outside Host_Frame: the engine's frame limiter (fps_max) and the platform loop. A frame's total is start to next start, so the timeline is wall-clock time.

Work counters

Version-2 file: 20 counters per frame (draws, prims, pb_dwords, tex_binds, v_world, v_studio, v_tri, v_2d, v_decal, world_faces, pvs_leaves, studio_models, studio_tris, lm_faces, lm_texels, water_verts, decals, particles, beams, sprites), added up by ref/nv2a where it submits the work and stored with each frame. Counts carry over from xemu to the console; times do not.
