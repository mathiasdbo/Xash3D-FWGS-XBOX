## Lessons

**New.** ALWAYS re-clean an auto-reapplying vendor-patch submodule before every `changed-files`/diff gate, not just the round that first diagnosed it — the gate cannot tell a patch reapplication from a real edit.

PR #152 (this run) published RED/BLOCKED on its terminal QA round (`gates-x9-x-studio-models-3/changed-files.log`) solely because `3rdparty/library_suffix` and `3rdparty/opusfile/opusfile` were dirty again, reapplied by `tools/xbox-cc.sh`/`xbox-cxx.sh`'s own preflight (`patches/library_suffix-xbox-subplatform.patch`, `patches/opusfile-xbox-stream.patch`; `docs/r3d/divergences.md` #5/#18) as a side effect of the same round's own `asset-studio-build`/`ref-isolate-nv2a` gates. The identical mechanism had already hit QA round 1 and been diagnosed and worked around (a second `git stash push -u`, run immediately after the compiling gates, specifically so a diff check would see a clean tree) one round earlier; the very next fix round ran the same compiling gates and did not repeat the workaround, so the following QA round had nothing left to fail on but this. A `changed-files` gate that runs after any gate compiling Xbox-side code must either exclude submodules known to carry this project's own self-healing patches, or the round that compiles must always re-clean them afterward — every time, not only the first time it is found, because nothing about running the same compiling gate again is different the second time.

Checked against `docs/r3d/lessons.md`'s existing headings: does not duplicate "NEVER treat a fresh git worktree as a build environment" (that is about missing built SDK output, not about a diff gate misreading a build tool's side effect) or "NEVER let the agent that ran a check decide whether it passed" (here the exit codes were real and correctly computed both times — round 1's RED and round 3's RED were both true reports of a dirty tree; the failure is in gate *sequencing/scope*, not verdict-computation). No other heading covers vendor-patch reapplication. Proposed as a new heading.
