## Lessons

**Second data point** for "NEVER diagnose a boot 'hang' from the halted CPU alone - find the last event the engine itself emitted" (`docs/r3d/lessons.md`, existing heading). Codex round 3 (confidence 0.98) found the implementer's own account attributed the background-release hang to ref/nv2a's texture lookup from exactly the evidence that heading already warns is insufficient: execution entering `ReleaseBackground`/`FreeWONBackground` plus a later frozen `host.framecount` and an EIP parked in the kernel idle thread (`CHANGELOG.md:34-39`) - promoted unchanged into `CHANGELOG.md:34-47`, `docs/r3d/design/x9-x-studio-models.md:241-248` and `docs/r3d/divergences.md:36` without ever tracing entry/return of `PIC_Free`, `GL_FreeImage`, `GL_FindTexture` or `nv2a_tex_check_name`, or checking for a `Sys_Error`/`Host_Error`/last-engine-event first. Same shape as the heading's own worked example (an idle CPU cannot distinguish a stuck free from thread exit, a restart, or another failure after the breakpoint), one run later, in a different subsystem.

**New candidate.** ALWAYS trace the call chain a shared engine predicate actually reaches for a given caller before designing a new behaviour around its name - a citation of one implementation is not proof of which one runs. Research's whole gating mechanism rested on `EngFuncs::ClientInGame()` meaning `cls.state == ca_active` (cited at `cl_gameui.c:1217`), used to distinguish "map is loading" from "paused/resumed." The predicate is checked at `3rdparty/mainui/BaseMenu.cpp:888`, one call after `UI_CloseMenu()` (`BaseMenu.cpp:876`) has already set the key destination to `KEY_GAME` (`BaseMenu.cpp:610-611`); the engine implementation actually reached from there returns true whenever key destination is `key_game`, unconditionally for multiplayer (`engine/client/cl_main.c:134-142`) - not from `cls.state` alone. Codex round 2 (confidence 0.99) found this gap on the first review pass; by then it had already shipped as the implementation's central condition. Checked against existing headings: not a duplicate of "NEVER trust a platform libc function you have not read or tested - a declaration is not an implementation" (`lessons.md` line ~77, about an nxdk pdclib stub that does nothing, a different failure shape - undeclared behaviour, not a differently-scoped one) or "NEVER design around 'the engine keeps this data in memory' without reading the XASH_LOW_MEMORY branch of its loader" (line ~1751, about a memory-truncation branch, not a predicate's caller-dependent semantics). Proposed as a new heading; a human should judge whether one occurrence here plus the general shape (a cited engine function used as a gate, without confirming what the actual call site resolves to) earns a place, or whether it is closer to a second data point for one of those two after all.
